# MT3UK site: notes for Claude

Static site for the MT3UK modified Tesla community, live at https://mt3uk.com. It is hosted on GitHub Pages and served through Cloudflare. A Cloudflare Worker (`workers/vote-worker.js`) handles votes, likes, comments, My Garage and the admin tools.

## Working rules

- **Ask before any commit or push.** Wait for an explicit yes each time. An earlier yes does not cover later changes, and an ambiguous instruction ("leave for now") is not permission.
- **Email Richard a summary of changes.** After a push, email a short summary of what changed to modtesla3uk@gmail.com (through the Gmail connector), ending with "Your next steps" and "My suggested next steps". The **Daily changes email** workflow (`.github/workflows/daily-changes-email.yml`, 16:49 UTC, also run by hand from Actions) emails him each evening what was pushed to `main` in the last 24 hours when there was anything besides bot syncs: `scripts/daily_changes.py` writes it from the commit titles and their bullet points, and posts it to the worker's `POST /admin/daily-summary` (admin key, the `VOTE_ADMIN_KEY` secret; sent to MT3UK, stopped by the Email switch). **In every commit message, add a `Next:` line for anything Richard has to do himself and a `Suggest:` line for a suggested next step**: the email gathers them into "Your next steps" and "My suggested next steps", with how the day's test runs went. Every summary to Richard, in chat or by email, ends with those two lists. Tests: `tests/test_daily_changes.py` and the block in `tests/track_worker_check.mjs`.
- **Remind Richard of open items when he interrupts.** If a message arrives while work is in progress, or he changes subject, say briefly what is still open before carrying on: anything uncommitted waiting for a yes, questions he has not answered, and steps he still has to do himself (for example setting lines on the Tracks panel).
- **Commit to `main`**, as there is no `dev` branch. If a push is rejected because the bots have added commits, rebase onto `origin/main` and push again. Never force-push.
- **The site is live.** A push to `main` deploys straight away, so verify changes locally first.
- **Run the tests** with `python -m pytest -q` (pytest-playwright, tests in `tests/`, the full suite takes about 12 minutes). Afterwards, check the "Run Playwright tests" workflow on GitHub. If you change copy, prices or markup, search `tests/*.py` for the old text or selectors and update them in the same commit.
  - **Smaller changes** (wording, colours, fonts, layout tweaks, a single feature, a small worker change): run only the tests that cover what changed, for example `python -m pytest -q tests/test_track_page.py tests/test_track_worker.py`, plus a browser check on phone and desktop for anything visual. Do not run the full suite. GitHub runs the whole suite after the push.
  - **Lots of big changes at once** (several features, or large changes to the worker, sign-in, likes, comments or uploads): offer to run the full suite and wait for a yes before doing so. Never run it unprompted.
- **Bump the `?v=` cache tag** on the `<script>` tag of any JS file you change (`track.html`, `admin.html`, `track-admin.html`, `leaderboards.html` and the other pages that load it), as the shared header and the track scripts are cached by browsers and Cloudflare under their old tag. A fix that does not bump its tag may not reach anyone for hours: the GPS repair and a filter that was later removed both went out without one.
- **Check mobile as well as desktop** for any layout change. The main mobile breakpoint is `max-width: 780px`.
- **Never use em dashes** in site copy, commit messages or anything else. Use commas, colons, brackets or full stops.
- **Anything that waits on an admin action gets a bell item and an email.** When you build a request, report or approval that Richard has to act on (on `admin.html`, `track-admin.html` or `events-admin.html`), always add it to that page's notification bell (counted, tagged New, opening its panel; `loadTrackBell` on `admin.html` also counts it if it lives elsewhere) and email MT3UK through `sendAdminEmail` in the worker, never `env.SEND_EMAIL` directly, so the Email switch covers it. Bring the bell up to date after the admin acts (`mt3uk-bell-refresh`), and add a test for both.
- **Notifications switches:** the top of `admin.html` and `track-admin.html` has **Bell** and **Email** switches (`js/admin-alerts.js`, `GET`/`POST /admin/alerts`, admin key, one KV key `admin-alerts`, `get()`). Bell off hides the bell on those pages; Email off stops every email to MT3UK about admin actions (`sendAdminEmail` checks it). Emails to members are not affected. Both start on. The same script keeps the bell current: `sendAdminEmail` (and undoing a Gallery request) bumps a stamp (KV `admin-alert-stamp`), the pages check it every 15 seconds while in view and at once when the page comes back into view, and a change fires `mt3uk-admin-changed`, which reloads what the bell counts (the full 3 minute reload stays as a back-up). So anything new for the admin must go through `sendAdminEmail` (with its subject and the admin page it belongs on) or call `bumpAdminStamp`.
- **Admin apps and push:** `admin.html` and `track-admin.html` can each be installed as their own app (`admin-manifest.json` "Admin", `track-admin-manifest.json` "Track Admin", each scoped to its own page only, because with the whole site as scope Chrome offers to open the installed MT3UK app instead; **Install** button in the Notifications row; Safari and Firefox are told how). **Push on this device** (per device, off until switched on) subscribes through the members' `/sw.js` and is kept on the worker as the push list of a pretend member, `ADMIN_PUSH_ID` (`push:mt3uk-admin`, through `POST /admin/alerts` with `subscribe` or `unsubscribe`); `sendAdminEmail` pushes the email's subject to those devices, whatever the Email switch says, and the tap opens the page it names. The browser's own subscription is never cancelled, because it also carries that browser's member notifications. On an iPhone push only works from the installed app.
- **Admin viewer token across addresses:** the sign-in handover (`POST /session/handover`, see Laps) also carries the admin viewer token (`X-Admin-Viewer`, with or without a sign-in; redeem gives it back after checking it), so a private session opens on mt3uk.com, laps.mt3uk.com or admin.mt3uk.com once the key has been entered on one. `js/account-bar.js` does it on the public pages; on the admin pages `js/admin-alerts.js` asks for the code when a link leaves the address (a Laps page goes to laps.mt3uk.com, anything else from admin.mt3uk.com to mt3uk.com) and redeems one on arrival, with `js/admin-key-keep.js` (in the `<head>`) taking the code out of the address first. Tests: `test_a_session_opened_from_an_admin_page_goes_to_laps`, `test_the_admin_viewer_token_goes_across_...` and `tests/laps_handover_check.mjs`.
- **admin.mt3uk.com:** on Android an installed MT3UK app claims every mt3uk.com page, so Chrome will not install the admin apps from mt3uk.com. They install from admin.mt3uk.com (a custom domain on the `mt3uk` Worker, same files): **Install** on mt3uk.com goes to the same page there (`#install`), once that address answers. On admin.mt3uk.com a link to any page but `admin.html` and `track-admin.html` goes to mt3uk.com (`js/admin-alerts.js`). **Remember the key on this device** (off unless switched on) keeps the admin key in localStorage (`mt3ukAdminKeyKept`), and `js/admin-key-keep.js` in the `<head>` puts it back each time, so the installed app opens ready. The admin viewer token for previews is per address, so previews on mt3uk.com still need the key entered on mt3uk.com once a month.
- **Nicknames are optional** (since October 2026): Profile opens without one (the old nickname gate is gone), the Nickname box in Your details can be left blank or cleared (`POST /profile` with an empty `nickname` clears it, `setNickname`), and the member then goes by their full name (`publicName`). A friend request needs a public name (nickname or full name), not a nickname. New members still get a nickname automatically (`initialNickname`), and a member from before that who has none gets one the first time `GET /profile` runs (`nicknameCleared` on the profile record stops it coming back once cleared), and **Give nicknames to members without one** on the Subscribers panel of `admin.html` (`js/nickname-fill-admin.js`, `POST /profile/admin/nicknames`, admin key, `handleProfileAdminNicknames`; it lists the profile records with `list()`, fine for an admin route) does it for everyone at once, reporting how many it gave. Tests: `test_profile_opens_without_a_nickname`, `test_nickname_can_be_cleared` in `tests/test_profile.py` and the block in `tests/mod_questions_check.mjs`.
- **Proofread new copy** for spelling and grammar before adding it, and before showing it to Richard. Use British spelling (colour, tyres, programme). Plurals never take an apostrophe: "modified Teslas", "the 2020s", "MOTs". An apostrophe is only for possession or a missing letter ("the Tesla's brakes", "who's quickest"). "Its" is possessive and "it's" means "it is".

## Worker

- `workers/vote-worker.js` deploys automatically through GitHub Actions on push to `main`, so there is no manual `wrangler deploy`.
- **Never use KV `list()` on a path hit per visitor or per page load.** Store data under a single JSON key and use `get()` instead. `list()` is only acceptable on admin or rarely hit endpoints. Search for `.list(` before committing worker changes and say you have checked.

## Site structure

- **Shared header and footer.** The menu, search and footer live in `partials/header.html` and `partials/footer.html`, with their styles in `css/site-header.css`. Edit those, never the copies in each page, then run `python scripts/build_layout.py` to copy them into every page. It also marks each page's active menu link (the `PAGES` map in the script) and turns links to a page's own sections into `#` links. `tests/test_layout.py` fails if a page has drifted. A new public page needs adding to `PAGES` there and in `tests/test_shop_section.py`. It also needs `js/notify-bell.js`, `js/messenger.js` and `js/signin-prompt.js` loaded (the bell, chat, profile and My Garage icons in the header; `js/notify-bell.js` adds the garage icon, `#nav-garage`, after the profile one). On a phone (up to 780px) the signed-in bar under the header (Profile, My Garage, Sign out, `js/account-bar.js`) is left off, except on Profile, so Sign out is still there.
- **Share buttons.** `js/share.js` adds a round share button to each page heading and section heading (`<section id>` with an `<h2>`, or `data-share-anchor`). Each links to a share page in `share/section/` with its own preview photo and intro text, written by `scripts/build_section_share_pages.py`. The sync workflow runs it, but after adding or renaming a section run it yourself, as `tests/test_layout.py` fails if a share page is missing. Use `data-share-image="images/..."` on a section to choose its preview photo.
- **Site search.** Pages and sections are listed in `data/search-index.json`; add an entry for any new page or section (`tests/test_search_index.py` fails otherwise). Owner Interviews are added to search automatically by `js/search.js` from `data/interviews.json` on their publish date. Their mods are searchable through `data/interview-search.json`: run `python scripts/build_interview_search.py` after adding or editing an interview.
- **Modern styling.** All new work uses the shared look in `css/site-header.css` (the "Shared look" block), not the old typewriter style:
  - Soft corners from `--radius` (10px), `--radius-sm` (8px) and `--radius-pill`. Light borders from `--hairline` and `--hairline-strong` rather than heavy ink lines.
  - IBM Plex Sans (`--font-body`) in normal capitals for buttons, labels, dates, badges and captions. Headings stay Archivo Expanded (`--font-head`). **Never use IBM Plex Mono (the typewriter font) or all-caps labels** in new or refreshed work.
  - Buttons: `.btn` plus `.btn-primary` (navy), `.btn-accent` (orange), `.btn-secondary`, `.btn-ghost` or `.btn-danger` (red, for Delete), with `.btn-sm` and `.btn-block`. Touch targets are at least 44px. Fields use `.field`, filters and tags use `.chip` (`.is-on` when selected), and boxes use `.card`.
  - Icons are inline line SVGs: `<svg class="icon" viewBox="0 0 24 24" aria-hidden="true">…</svg>`. Never use text characters as icons (`&times;`, `&larr;`, `&lsaquo;`, `&rsaquo;`, `&#9662;`, `▼`). On/off settings are switches, not checkboxes.
  - Pages move onto it a batch at a time. The refreshed ones are listed in `REFRESHED` in `tests/test_style.py`, which fails if they bring back the typewriter font or text-character icons. When you refresh a page, or make a new one, add it to that list. When editing a page that hasn't been refreshed yet, use the modern style for anything new and ask whether to refresh the rest of the page.
- **Track Days guides** (`track-day-venues.html`, `track-day-prep.html`, `track-day-on-the-day.html`, reworked October 2026 to be shorter): short cards, chips and folding rows from `css/track-guides.css` (`.tg-cards`, `.tg-tests`, `.tg-fold`, `.tg-next`, and `.tg-laps`, the navy Laps card). Each venue has a Charging row and a "Tests" row of chips. **Laps strips** (`js/laps-strip.js`, `css/laps-strip.css`): any MT3UK page can drop in `<div data-laps-venue="thruxton"></div>` for a track's live Laps boards (fastest, who, how many cars, See the leaderboard, Add your session; an invitation when nothing is shared) or `<div data-laps-more></div>` for the other tracks on Laps, from `/track/counts` and `data/tracks.json`, links carrying `data-laps`. `[data-laps-fast-line]` (the homepage Sessions tile's grey line) shows "Fastest at <track>: <time>, <driver>" from the busiest board. **While Laps is an early preview**, any `[data-laps-add]` link (the venues' Add your session, On the Day's Add a session) becomes **Join the early preview** for a visitor who is signed out (to `laps-signin.html`, whose sign-up puts them on the list) or a member who has not asked (to `track.html`, with its request form), and **You're on the list** for one waiting; `GET /track/access`, kept for the browser session in `sessionStorage` `mt3ukLapsAccess`. While Laps is a preview (`preview` from the public `GET /laps/signin`, `mt3ukLapsPreview`) each strip's heading carries an **Early preview** tag, and any `[data-laps-preview]` (in each strip, On the Day's Laps card, the Gallery car sheet's strip for the owner, and `#lb-preview` at the top of the Leaderboard) shows a short note for anyone without early access: the leaderboards are open to everyone, adding your own laps is for early testers. The Leaderboard's **Add a session** (`#lb-add-session`) is gated the same way. Once Early access is open to all, none of it shows. **The note's words** are the Welcome text panel's **Early preview note** boxes on `track-admin.html` (`previewOut`, `previewNone`, `previewPending` in `track-copy`, read from the public `GET /track/copy`; blank keeps the built-in words in `js/laps-strip.js`). Tests: `test_the_track_day_venues_page_...`, `test_members_with_early_access_...`, `test_members_waiting_for_early_access_...`, `test_the_leaderboard_invites_...`, `test_nothing_is_said_about_the_preview_...` and `test_the_homepage_sessions_tile_...` in `tests/test_laps_home.py`. **The Gallery's car sheet** (Full list in the photo viewer, `drawCar` in `gallery.html`) draws the car's shared bests (`track` from `/cars/public`) as a Laps strip, "<car> on Laps": each track with Best lap, Best run or Quarter mile, the date and the time, linking to the session, then All shared sessions and What is Laps? ## Owner Interviews (blog)

- `data/interviews.json` drives the homepage hero, the next interview card, the interview list, the announcement bar and `blog.html`. What shows depends on the UK date and each entry's `publish` date. Add `?date=YYYY-MM-DD` to preview a future date.
- Each interview is a root-level `blog-<slug>.html` page. Its images live in `images/blog/owner-interviews/<slug>/`.
- For a new interview:
  - add its entry to `interviews.json`
  - add the page to `PAGES` in `generate_sitemap.py`
  - add the page to `PAGES` in `scripts/build_layout.py` (active link `blog.html`), then run the script to give it the shared header and footer
  - run `python scripts/build_interview_search.py` so its mods are searchable
  - add the comments block: `<div class="ic" id="comments" data-thread="<slug>">` with `js/interview-comments.js`
  - add `<script src="js/interview-gate.js"></script>` in the `<head>`, after the viewport meta. Until the publish date the page asks for a one-time code, which anyone can have emailed, like Sign In. A code opens it for 4 hours (and makes that email a member if it is not one already). The admin page (Interview previews) lists who has opened each one and can revoke access. The gate is off on localhost; add `?gate=on` to try it.
- Comments run in demo mode on localhost, stored in localStorage. Add `?comments=live` to use the real worker.

## Event pages

- One page, `event.html?e=<slug>`, shows every event. `js/event-page.js` draws it from that event's entry in `data/event-pages.json` (title, tagline, dates and times, venue, images, description, tickets, running order, FAQ). A section with nothing in it is left out, and a draft shows striped image placeholders. There is no per-event HTML file to copy.
- **Make and edit events on `events-admin.html`** (Event pages): a form for every field, image uploads (shrunk in the browser, stored in the R2 bucket under `events/<slug>/`), Save, Preview, Publish now, Schedule, Draft and Delete (not while live). Do not hand-edit the JSON unless you have to. Entries in `images/events/` are fine too.
- Each entry is a draft (`"draft": true`, no publish date) or has a `publish` date (UK time). `js/event-gate.js` shows only a Coming soon card until then. It can be opened early these ways. **Admin:** entering the admin key on `admin.html`, `track-admin.html` or `events-admin.html` leaves a month-long "admin viewer" token in that browser (tied to the current admin key, so changing the key ends them all), and unpublished events and Owner Interviews then open there straight away with a small "Admin preview" note. Preview on `events-admin.html` still makes a one-time link that keeps one event open until **End preview**. **People you share it with:** **Copy link** on the event, and anyone with the link can have a one-time code emailed on the gate card, like Sign In and the Owner Interviews. A code opens it in that browser for 7 days, signs them in and makes that email a member if it is not one already (the card and the email say so). Members can instead press **Use a passkey** (if they have set one up in Profile) or **Continue as ...** (if already signed in): a sign-in proves the email just as a code does. The Owner Interview gate has the same options. **Event previews** on `events-admin.html` lists who has opened each event and can revoke or restore an email. There is no countdown. An event not in the file, or a failed read of the file, stays hidden. The gate is off on localhost; add `?gate=on` to try it.
- Save writes `data/event-pages.json` (one commit, so the live site updates in about a minute) and a copy in KV, which Preview reads so a change shows straight away. Publish state changes only through the actions.
- On `events-admin.html` an editor (the event page form or the older event form) opens directly under the event being edited, whose card gets an outline and a small arrow beside its title. It moves back when closed and stays put when a list redraws after a save.
- The older Facebook-style events (`events-data/events-manifest.json`, the Upcoming and Past lists on `events-admin.html`) each have an event page too, linked by `manifestId`. **Edit** on one opens the full event page editor (all the fields, images and ticket options), filled in from the event, or from its page if it already has one; saving also updates the older entry (name, dates, place, link and description) so the meets list and the page agree. **Quick edit** opens the small form under the event (mainly for the attendee counts). There is no separate way to add an older-style event any more: add events with **Add an event page**, and the homepage shows a page-only event like any other. The upcoming events start as drafts in `data/event-pages.json`. Once a page is live, the homepage shows the featured card instead of the older row (and a past one links to the page).
- Live events are featured on the homepage Events section (card image and tagline) until `endDate` (or `startDate`) has passed.
- Worker routes are under `/events/pages/`. Tests: `tests/test_event_pages.py` (browser, mocked worker) and `tests/test_event_worker.py` (runs the real handlers in node).
- Link previews (WhatsApp, Facebook, X, iMessage) read a page's own HTML and do not run scripts, so `event.html?e=<slug>` can only show one fixed preview (the MT3UK logo). Each event therefore has a share page, `share/event/<slug>.html`, with its own title, when and where, and image (hero, else card, else poster), which sends people on to the event page. `scripts/build_event_share_pages.py` writes them from `data/event-pages.json`. They **must be committed** (`share/event/`): mt3uk.com is served from the files in the repo (see `wrangler.jsonc` and `.assetsignore`), not from the GitHub Pages build, so anything only generated in `pages.yml` never reaches the live site. The "Sync gallery and track days manifests" workflow runs the script whenever `data/event-pages.json` or `images/events/` changes and commits the result, as it does for the other share pages (`pages.yml` also runs it, harmlessly). It also makes a 1200 x 630 preview picture under 300 KB for each event (`share/event/<slug>.jpg`), because WhatsApp drops preview images much over that and event photos are usually bigger. The event page has a **Share** button that copies or shares the share address. **Copy link** on `events-admin.html` copies that address, so always share that one, not `event.html?e=...`. A live event also has a **Share** button there, which opens the phone or browser share sheet with the same address (or copies it). Chat apps cache previews, so a link already shared may keep its old picture for a while.

## Track sessions: tyres

- The tyre makes, their models and the Width, Profile and Diameter choices are in `data/tyres.json`. `js/tyre-data.js` loads it with the worker's changes on top (`/tyres`) and joins or splits a description such as "Michelin Pilot Sport 4S, 245/35 R19".
- **Edit them on the Tyres panel of `track-admin.html`** rather than by hand. ## Track sessions: brake pads, maker data and Compare

- **Brake pads** are in `data/pads.json` (makes, each with compounds; Original equipment first) and `js/pad-data.js` (`MT3UKPads`) loads it with the worker's changes on top (`/pads`, KV `pad-library`, `get()`), as for tyres. Each compound can carry what its maker publishes: `use` (Road, Fast road, Track day, Endurance, Race), `mu`, `tempMin`, `tempMax` (degrees C) and `notes`. **Never invent the figures**: leave them blank until taken from the maker. Edit them on the **Brake pads** panel (Content group of `track-admin.html`, `js/pad-admin.js`, `GET`/`PUT /pads/admin`, admin key, `cleanPadLibrary`).
- **Pads on a session:** the Add page and Session settings have Front pads (make and compound drop-downs) and a **Same pads on the rear** switch (`padFields`, `readPads`, `padPayload` in `js/track-page.js`). The Add page starts from the car's My Garage brakes fields (`carPads`, `specs.brakes.fields.frontPads`/`rearPads`, read with `MT3UKPads.parse`); changing them does not change the garage. The session keeps `padFrontMake`, `padFrontCompound`, `padRearMake`, `padRearCompound` and a built `pads` ("Pagid RSL29", "Original equipment pads", "Front: X, rear: Y", `composeTrackPads`), kept through re-uploads and re-times, and shown under the session heading (`#tp-pads-line`).
- **Tyre maker data:** **Maker data** on a make's row of the Tyres panel (`openInfo` in `js/tyre-admin.js`) sets, per model, category, the label's wet grip and rolling resistance (A to E), noise (dB), EV rated and notes, kept in the tyre library as `info` keyed `Make|Model` (`cleanTyreLibrary`); `MT3UKTyres.info(make, model)` and `makerLine` read it.
- **Kerb weights:** set in a make's Edit form on the Vehicles panel, per model and (when it differs) per variant, kept in the vehicle library as `weights` (`make|model` or `make|model|version`, lowercased, 300 to 4,000 kg; a save without them keeps them). `MT3UKVehicles.weight(v)` gives the variant's, else the model's. `data/vehicles.json` carries the file's `weights` (found by web search, October 2026) and `data/tyres.json` the file's `info`. **A car's own kerb weight** (a stripped car) is set by the owner in the Kerb weight box on the open car's row in My Garage (`#mb-car-weight`, the vehicle list's figure as its placeholder, sent as `weight` only when typed, kept in `car-details` by `cleanCarModel`, 300 to 4,000 kg) or by the admin on the Members' cars panel (`.mc-weight`), which also shows the pads fitted (`carPadsText`, from the Brakes section of the car's mods); the board entry carries it (`weight`) and `weightOf` in `js/leaderboard-page.js` uses it before the vehicle list's. **A car's page on Laps** (`showCar`, `carKitHtml`, `#tp-car-kit`) says the kerb weight (owner's figure, else maker's figure from the vehicle list) and the pads fitted (`car.pads` from `/track/public`), and each session row names the pads it was run on. Tests: `test_a_build_page_shows_its_kerb_weight_and_pads`, the Members' cars and My Garage tests in `tests/test_vehicles.py`, and the worker checks.
- **Board entries** carry, in each of `bests` (now one per conditions, tyres and pads, up to 16), the pads, the air temperature (`temp`), peak braking g (`brakeG`) and the hottest brake temperature the car reported (`brakeTemp`).
- **Compare tyres and Compare pads** on a board of `leaderboards.html` (the view chips `#lb-views`; no pads view on drag boards; `groupResults` and `compareHtml` in `js/leaderboard-page.js`): each tyre (or pad) with the number of cars, best and typical (median) time and the gap to the quickest, marked "Few cars" under 3, with the maker's figures beside it; Compare pads adds peak braking g and brake temperature, warning when it was hotter than the pads' working range. **Same car, different tyres (or pads)** pairs a car's bests on two of them. Filters for driven wheels, air temperature (cold under 10, mild 10 to 20, warm over 20 degrees C) and weight (light under 1,800, mid to 2,100, heavy over 2,100 kg, shown only when weights are known) apply to every view. Tests: `test_compare_tyres_and_pads_on_a_board`, `test_pads_start_from_my_garage_...`, `test_admin_brake_pads_panel`, `test_admin_tyres_maker_data` in `tests/test_track_page.py`, and the blocks in `tests/track_worker_check.mjs` and `tests/vehicle_worker_check.mjs`.

## Vehicles: makes, models and type

- The vehicle makes, their models and their type (car or bike) are in `data/vehicles.json`, **electric vehicles only** (since October 2026: petrol models such as the 911, M3 or Civic Type R, and petrol bikes, were taken off; cars already saved with them keep them). `js/vehicle-data.js` loads it with the worker's changes on top (`/vehicles`), as for tyres. A make has a type, so one make can be both a car and a bike make. A make changed on the Vehicles panel keeps its own stored list of models, so the file's list only reaches it after **Use the built-in list**. - **Why is a session not on a leaderboard?** On the Problems and checks panel of `track-admin.html`, paste a session link or id and press **Check** (`GET /track/admin/boardcheck`, admin key, `handleTrackAdminBoardCheck`, one board key read with `get()`): it says which board the session belongs on (Track days, Sprint, Hill climb or Drag), whether its car is a row on it, and the reasons if not (sharing is Only me, no track or layout matched, a request still waiting, the track listed as another kind, taken off by the admin, or the car's fastest is another session). **All leaderboard problems** on the same panel (**Find problems**, `GET /track/admin/boardproblems`, admin key, `handleTrackAdminBoardProblems`: it lists the first 700 members' session lists with `list()`, which is fine for an admin route, and each board once) shows every shared session that is not on a board for a fixable reason, with the reason (same `trackBoardWhy` as the single check), plus any board that has entries but no count in `track-board-counts` (the track list hides such a venue as having no sessions). **Repair** (`POST /track/admin/boardrepair`) either runs `refreshTrackBoard` for a board's cars so its count, top three and entries are right, or, given a `sessionId` (the Repair button on a problem row or on the single check), writes the member's list, the car's shared list and the board again from the session's own record (`putTrackIndexesFor`). The single check also says when the car's shared list does not have the session or the track list is not counting the board, and offers Repair. A session whose track or layout has gone from the track list (renamed, removed and added again) is a problem even when its car still has a row on the old board, because the leaderboard cannot list that board: Repair finds the listed track it looks like by name (ignoring words such as hill climb, sprint and circuit) or place, and the layout by length, links the session and the member's other sessions at that gone track to it (`trackRelinkCandidate`), and refreshes the old board; with no match it says to add the track on the Tracks panel.
- Most layouts have no official line yet. The first member's request (kept one per course) shows in the Admin bell; **Approve and add track** sets that layout's official line from it (or adds the course), after checking it on **Open map**. Until then the member's own line times it and the layout is matched by length.
- **Admin shortcut:** on the Add a session page, once the admin has set and confirmed a member-style start and finish, **Make official** (`POST /track/admin/course`, admin viewer token) saves them as the course's official lines at once, so the next upload of the same course is timed on them without waiting for a request.
- **Nothing blocks a save.** A sprint, hill climb or track day whose lines give no runs can be saved with **Save without times, tell MT3UK**: it is stored as a mapped drive (`type: other`, `pendingCourse` set, private) and a request goes to the Admin bell. Once the course is added, the member changes its type in Session settings and it is timed. A drag run at a strip we do not list is saved too (`unlisted`: private, no leaderboard) and the strip is requested automatically.
- **Drag runs** show 0 to 30, 0 to 60, 60 to 100, eighth and quarter times, timed from the first movement. The **1 ft rollout** switch on the Add page starts the clock once the car has moved one foot (as strip lights and RaceBox's option do); the session keeps `rollout`. A street run (admin testing) also keeps and maps the path of the drive (`outline`, kept for street runs only).
- **Track days need no start line from the member.** With no official, file or member line, `autoLapLine` in `js/track-parse.js` finds the lap line from the trace (`session.autoLine`); the member is only asked to tap a line if the file has no repeated pass (a single lap). Sprints and hill climbs still need a start and a finish.
- **A track or sprint we do not list needs a name.** The Track name box on the Add page (and the strip name for a drag run) is required, while a drive's Where was it? stays optional: Save stops on an empty box and points at it (`missingName` in `js/track-page.js`), and the worker refuses a track day or sprint with no `venueId` and no name (`handleTrackSessionSave`, 400). The admin renames such a session on the **Member sessions** panel of `track-admin.html` (`js/track-member-admin.js`, `POST /track/admin/session`, admin key); a session at a listed track takes its name from the track list, so it is renamed on the Tracks panel.
- **Members can add a new track themselves.** When a track day or sprint has lines but no listed course, the Add page shows an **Add this track now** switch (`addNowHtml`, off by default). Saving then calls `POST /track/courses` (`handleTrackCourseAdd`, behind the early preview gate), which builds the venue or layout from the member's lines exactly as **Approve and add track** does, flagged `review: true`, and keeps the request in the Admin bell marked `added`. The page re-times the session on the new course (`addCourseNow`) and saves it, so it is on the leaderboard at once. The Tracks panel shows "Added by a member, to review" and the request card has **Mark reviewed** (action `approve`, which clears the flag) and **Edit the track**. The admin gets an email.
- Sprint ignore switch: skips the first finish crossing after each start, when that run crosses the finish more than once. "Run ends on" picks a crossing by number instead. A saved session keeps its file name (`fileName`, shown only to its owner and the admin view). Peak g ignores one-reading spikes and cornering below 15 km/h.
- **Editing a saved session's start and finish lines** is a permission, per session, that the admin gives and takes back (`js/track-page.js` `lineEditHtml`, the **Line editing** panel of `track-admin.html` in `js/track-lines-admin.js`, routes `/track/lines/status`, `/request`, `/propose` and `/admin` in the worker). The member presses **Request Edit Map** on their session (one with saved readings; a sprint, hill climb or track day; a session whose readings were not kept shows why instead, with an **Add the readings again** button (`readingsAgainHtml` in `js/track-page.js`: the member picks the same file or files, they are read and joined as on the Add page, checked against the session's length, distance and place, and sent to `POST /track/session/source`, so there is no duplicate session), and the saved banner says so when the worker refused them: `keepReadings` in `js/track-page.js` reports `{ kept }`, the worker keeps at most 6 MB gzipped or 22 MB unzipped, and says which limit was hit (also over 400,000 readings); a refusal is kept on the session as `readingsRefused` (shown to its owner and the admin only, so the reason survives a refresh, and cleared once readings are kept) and emails the admin who tried it, the session, the file name and the reason (`refuseTrackSource`, the first three tries per session); each reading is sent without its empty trailing columns, and a slow upload that finishes after the page has moved on brings the session up to date), and the admin is emailed, with links to `track-admin.html#lines-<session id>` (which opens the Line editing panel and marks that request, on a fresh load or when only the address's end changes) and to the session. The email about a change sent for approval has the same two links. **Allow** switches the map editor on for that session and emails the member, and the panel lists who has access to which map. Requests waiting and changes to approve also show in the admin notification bell (groups "Map edit requests" and "Map changes to approve", built from the panel's rows by `data-state` and `data-key` in `js/track-admin-page.js`; a new change counts as new again). The member moves the lines on the map picker (the Add page's, via `a.lineEdit`, which times with only the lines on the map: `ownLines` in `js/track-parse.js`) and presses **Send for approval**: nothing on the session changes, and the admin is emailed (subject "Map edit awaiting your approval") the lines and time from and to, as an HTML email with the old lines and the new lines pictured on the satellite map (`js/track-line-image.js` draws two 1000 x 600 JPEGs in the member's browser on the same view, falling back to the drive's trace on a plain background if the tile server will not share its imagery with a canvas; they go to `POST /track/lines/image`, are kept in KV for at most a month, and are shown on the panel and removed when the change is accepted, undone, declined or revoked). The email is built as `multipart/related` with inline pictures (`rawEmailWithImages` in the worker) and a plain text version, and a change whose email could not be sent is flagged on the panel. **Accept** works the time out again in the admin's browser from the saved readings on those lines (never the member's figure) and shows the result, with what else it will change, in one confirm. On a session at a listed course (`findCourse` in `js/track-lines-admin.js`: its course, else its organiser's, else the track's only one) it then makes the member's lines that course's official lines (`/track/admin/course` with `replace`, which now also takes the admin key), re-times the member's own session on them, and re-times every other session at the track through `window.MT3UKTrackAdmin.retimeTrack` (the Tracks panel's Re-time sessions here: from saved readings, a time moving over 10% held back, then the leaderboards rebuilt). A session on no listed course changes alone and is marked `linesAccepted` so later re-times keep its lines; **Undo** throws the change away; **Revoke** switches the editor off. A member cannot save moved lines any other way: the worker refuses a changed start or finish line on `PUT /track/session` (a change of type does not move the lines). The list is one KV key (`track-line-access`, `get()`, no `list()`), and `/track/admin/retime` (one session) and its readings also accept the admin viewer token, while its list of every session stays on the admin key. Official lines of a course are still edited on the Tracks panel, and the `Make official` shortcut can now replace them in place (`replace` and `layoutId` on `/track/admin/course`).
- **Renaming the track on a session** uses the same gate for a session at a track we do not list (no `venueId`, so its name is what the member typed; a session at a listed track takes its name from the track list). The member's session page has a **Track name** box (`renameHtml`, `drawRename` in `js/track-page.js`): **Request rename**, then once allowed the member types the name and presses **Send for approval**. Routes `/track/rename/status`, `/request` and `/propose` (behind the early preview gate) and the admin side on the same `/track/lines/admin` route with `kind: 'rename'` (`handleTrackRenameAdmin`): its GET adds rename rows (`kind: 'rename'`, `current`) to the Line editing panel, which shows them marked **Rename the track** with Allow, Accept, Undo and Revoke. **Accept** changes the name on the worker (`rec.venue`, then `putTrackIndexesFor`), so only that session changes, and emails the member. The list is one KV key (`track-rename-access`, `get()`, no `list()`), kept apart from `track-line-access` so a session can have both. The bell has "Track rename requests" and "Track renames to approve" groups.
- **A hill climb saved at a track the list has as a plain sprint** marks that track as a hill climb (`markHillTrack`, on save and on a change in Session settings), because the leaderboard tab follows the track, not the session. The admin is emailed so a wrong choice can be put back on the Tracks panel. The board check's tab is the one the leaderboard uses (the track's), and Repair does the same marking.
- **The session ID** is shown under the heading of a session to its owner and the admin view (`#tp-sid`), with a **Copy** button (`copyText` in `js/track-page.js`), so it can be pasted into the checks on `track-admin.html`.
- **Start and finish the wrong way round:** the drive back down a hill retraces the climb, so a member can tap the lines in the wrong order and get the slow drive down timed instead of the climb. `sprintSession` in `js/track-parse.js` also pairs finish-then-start crossings of the same lines, and when the fastest of those passes has a peak speed at least 1.3 times (and 15 km/h over) that of the runs timed it sets `reverseRun` (`peak`, `time`, `fwdPeak`, kept by `cleanTrackSession`). The Add page and the owner's session page then show a warning (`reverseHtml`, `#tp-reverse`). It is a warning only: nothing is changed or blocked. `tests/fixtures/shelsley-climb-and-descent.vbo` is a trimmed real file with both passes (`ANALYSIS_VERSION` 8).
- **Refresh button** (`refreshChip` in `js/track-page.js`, `data-refresh`) on the member's list of sessions, a session and a car's page: it fetches the page's own scripts, styles and `data/tracks.json` again with `cache: 'reload'`, clears the service worker's stored copies and asks it to update (it never unregisters it, because `sw.js` carries push notifications), then reloads the page on the same view. It is for a member whose page looks out of date.
- **The line picker on the Add page and the edit-the-map screen** keeps its zoom and centre when a marker is placed or moved (`drawTap` carries `zoom.frac()` over from the previous map held in `add.tapMap`), so the member can see exactly where the line sits. Under the map a **Line figures** card (`lineFiguresHtml`, `#tp-figs`) shows both ends of the start and finish lines as full latitude and longitude figures to 7 decimal places with a **Copy** button each; when a saved session's map is being edited it shows Before and After side by side, so they can be checked before **Send for approval**.
- **A standing start is timed from move-off** (sprints and hill climbs, `sprintSession` in `js/track-parse.js`, `ANALYSIS_VERSION` 9): the clock starts at the first reading above 0.5 km/h after the stop, using the file's own time column, as a VBOX does. The start line only picks out the run (it must be crossed within 25 s of the move-off), so where it sits never changes the time; only the finish line decides where the clock stops (found from the positions, interpolated between two readings). On the Shelsley Walsh file the finish line at 52.2598990, -2.4135109, 52.2598692, -2.4138598 gives the VBOX time of 33.05 s from any start line. A run that does not start from a stop still starts at the line crossing. **The accelerometer or the speed, whichever moves first** (`ANALYSIS_VERSION` 14, October 2026, asked for by John Chambers): the speed column of some loggers (Tesla Track Mode) lags the car, so `launchFromG` in `js/track-parse.js` also reads the recorded lengthways g (never g worked out from the speed, `gDerived`, which lags the same): the standing level is the median g over the stop (a hill start sits on a slope), and a reading `LAUNCH_G` (0.15 g) over it for `LAUNCH_HOLD` (2) readings in a row, within `LAUNCH_LOOK` (3 s) before the speed rose, starts the clock instead when it comes first. The three constants sit beside `ANALYSIS_VERSION` for tuning. The session keeps `launch` (`from`: `g` or `speed`, `lead`: seconds the g launch was ahead) for the best run, kept by `cleanTrackSession`, and the session page says it under the heading (`#tp-launch`, `launchLine`). Drag runs are not changed. Tests: the version 14 block in `tests/track_parse_check.mjs` (a copy of the Shelsley file with its speed 0.3 s late keeps the 33.05 s), the `launch` block in `tests/track_worker_check.mjs` and `test_a_sprint_says_which_signal_started_its_clock`.
- **G-force chart peaks:** there are three chips, Acceleration G, Braking G and Cornering G (`G_DEFS`); there is no Speed chart, because four stacked charts squeezed the g scales: each lap's speed is written above the cursor on the top chart (`speedAtCursor`, `.tp-gspeed`, blue for lap A and orange for lap B, in the chart's top margin) and shows and hides with it. Braking G (`brk`) is the lengthways g below zero drawn upwards, from 0 g to the hardest stop, with its own dashed max line and dot; the Acceleration chart still shows both sides. The Acceleration G, Braking G and Cornering G charts on a session (`drawG` in `js/track-page.js`) plot the lap trace's readings as recorded (about 5 a second, not averaged: averaging flattened short peaks, so the line stopped below the headline figures), and draw each lap's biggest figure as a dashed line with a dot on the peak (the `.tp-gpeak` dots). The figures are not drawn on the chart, because on a small screen they landed on the traces: they are listed under the charts in `#tp-gpeaks` (one line per chart, `.tp-gmax` for each figure), and left out in full screen to keep the map's room: cornering has a single maximum, whichever way it was ("Max A 1.26 g, B 1.22 g"), and the Acceleration chart has "Max acceleration" and "Max braking". The labels use the same raw figures as the note under the charts and the headline tiles. Holding or hovering on a G chart reads the recorded row nearest the finger (`nearRow`), not a blend of two rows, so the reading (the tooltip, the Accel and Corner figures under the map, and the dot) can reach the Max figure; a blend of two 5 a second rows can never land on a peak that sits on one row.
- **Lap trace g figures keep the real peaks** (`lapTrace` in `js/track-parse.js`, `ANALYSIS_VERSION` 11): a lap trace is kept at 5 readings a second whatever the file's rate, and each row's cornering and lengthways g is the biggest (either way) of the readings in its 0.2 s step, a reading more than 0.25 g from the middle of it and its two neighbours is a glitch and is replaced by that middle value, and every other reading is used as recorded; the hundredths round half away from zero (RaceBox's 0.94 g braking is a recorded -0.935). `ANALYSIS_VERSION` 12. Checked against a real RaceBox file (Castle Combe, lap 3): cornering 1.26, acceleration 0.46 and braking 0.94 g, as RaceBox shows. Before, only the reading that started the step was kept, so on a 25 a second file the peak of a corner could fall between kept readings and the charts, tiles and note stopped a hundredth or two short of the file's real figure. A saved session picks it up on a re-time or a re-upload. `tests/track_parse_check.mjs` has a case that fails on the old way.
- **Drag runs that stop short of 60 mph:** a launch that reaches 30 mph is listed as a run (`dragRuns` in `js/track-parse.js`, `ANALYSIS_VERSION` 10; the worker's `cleanTrackRuns` keeps a run with `s30` or `s60`), with a dash for the figures it did not reach, as RaceBox lists it. It used to be dropped unless it reached 60 mph, so a 9-run RaceBox session showed 7. Creeping about (never reaching 30 mph) is still not a run. Best 0 to 60 and the notes only look at runs that have one; the speed chart shows up to 12 runs. `tests/track_parse_check.mjs` has a two-launch case.
- **GPS glitches** are mended when a file is read (`repairGlitches` in `js/track-parse.js`): a fix that drifts back along the road, freezes or creeps at half pace at speed and then jumps to catch up has its readings since the last good fix put onto the line to the first good one, spaced by the distance the speeds give. Times and speeds are untouched, a real hairpin or a standing car is never touched, and a lost signal (over 5 s) is left alone. A saved session only picks it up on a re-upload or **Re-time sessions** on the Rebuild and re-time panel of `track-admin.html` (`ANALYSIS_VERSION` goes up with each change here). `tests/fixtures/abingdon-glitches.csv` holds the real patches it was built on, and the clean fixtures must stay at zero readings moved. Mend the data, never the drawn line: a filter in `js/track-view.js` once deleted a whole corner from the compare map.
